# AUTOSAR HLD AI Assistant

An intelligent, context-grounded AI assistant engineered for automotive software architects and functional safety engineers to analyze AUTOSAR Classic and Adaptive High-Level Design (HLD) specifications using Retrieval-Augmented Generation (RAG).

---

## Overview

The **AUTOSAR HLD AI Assistant** is a specialized engineering copilot that ingests multi-page automotive architecture PDF specifications, extracts structural text, headings, and interface tables with OCR fallback, indexes dense vector representations into a local ChromaDB store, and delivers strictly grounded answers with traceable page-level citations.

Every statement generated by the assistant is tied directly to verified evidence from ingested High-Level Design documents, eliminating ungrounded hallucinations while enforcing human-in-the-loop engineering governance.

---

## Problem

Automotive High-Level Design (HLD) specifications frequently span dozens or hundreds of pages and are maintained as unstructured PDF documents describing:
- Software Components (SWCs), ports, interfaces (Sender-Receiver, Client-Server), and signals
- Runnable execution periods, timing requirements, and debounce filters
- End-to-End (E2E) protection profiles and ISO 26262 functional safety constraints
- Multi-version architectural evolution across vehicle software releases

Manual document search and verification across revisions is tedious, error-prone, and time-consuming. General-purpose LLMs cannot be trusted with safety-critical automotive architecture because they suffer from hallucinations, lack document version awareness, and fail to provide auditable source traceability.

---

## Key Features

The assistant implements the following verified, production-ready capabilities:

- **AUTOSAR HLD PDF Upload & Validation**: Fast upload with SHA-256 deduplication and PDF integrity validation.
- **Page-Level PDF Extraction**: Native page-by-page extraction of text, architectural headings, and interface tables using PyMuPDF.
- **Scanned-Page OCR Fallback**: Automatic image rendering and Tesseract OCR fallback for scanned or image-based pages.
- **Context-Aware Semantic Chunking**: Heading and section boundary preservation with table-to-Markdown formatting.
- **Sentence Transformer Embeddings**: Dense 384-dimensional vector embeddings generated using `all-MiniLM-L6-v2`.
- **ChromaDB Vector Storage**: Persistent local vector indexing with document UUID and architectural version isolation.
- **Semantic Retrieval**: Top-K cosine similarity retrieval with similarity threshold pruning.
- **Grounded RAG Question Answering**: Strict context-grounded generation adhering to retrieved evidence.
- **Document & Version Filtering**: Scope queries to a specific document or compare revisions (`v1.0`, `v2.0`).
- **Traceable Page-Level Citations**: Granular citations with source filename, version tag, page number, section heading, similarity match score, and evidence snippet.
- **Interactive Citation & Page Inspection**: Direct page viewer modal enabling instant verification of source page text and tables.
- **Insufficient-Evidence Refusal**: Deterministic refusal when evidence is absent, preventing architectural hallucination.
- **Human-in-the-Loop Governance**: Designed as a verification assistant that informs engineers without unauthorized automated approvals.
- **Configurable LLM Providers**: Multi-provider support including Mock (offline/local deterministic mode), OpenAI, Anthropic, Gemini, and Ollama.

*(Note: Advanced automated graph generation, AST extraction, automated rule-based inconsistency detection, and automated compliance sign-off are designated for future roadmap phases and are not claimed as completed).*

## Setup & Running

### Prerequisites
- Python 3.10 to 3.13 (Python 3.13 verified)
- Node.js 18+ (Node 20 LTS recommended)
- Tesseract OCR (optional, required only for scanned image PDF fallback)

### 1. Backend Setup (Windows PowerShell)

```powershell
cd backend
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt

# Create .env from template (defaults to offline mock LLM provider)
copy .env.example .env

# Run FastAPI backend server
uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

- **Backend API**: `http://127.0.0.1:8000`
- **Interactive Swagger Docs**: `http://127.0.0.1:8000/docs`
- **Health Check**: `http://127.0.0.1:8000/health`

### 2. Frontend Setup (Windows PowerShell)

```powershell
cd frontend
npm install
npm run dev
```

- **Web Application**: `http://localhost:5173`

The frontend Vite server automatically proxies `/api` and `/health` requests to `http://127.0.0.1:8000`.

## Demonstration Inquiries

The system includes pre-configured sample AUTOSAR High-Level Design documents (`AUTOSAR_BodyControl_HLD_v1.0.pdf` and `AUTOSAR_BodyControl_HLD_v2.0.pdf`). Below are verified queries and expected behaviors:

### 1. Runnable Timing & Constraints
- **Question**: *"What is the cycle time of Run_ReadDoorSensors?"*
- **Grounded Answer**: Runnable `Run_ReadDoorSensors` has a cyclic execution period of **20 ms** (validating a 50 ms debounce timer) and is mapped to `DoorControlSWC`.
- **Traceability**: Citations pointing to Page 3 and Page 2 with interactive page inspection.

### 2. Component Interface Connectivity
- **Question**: *"Which software components are involved in DoorStatus_If?"*
- **Grounded Answer**: `DoorControlSWC` (provider via P-Port `P_DoorStatus`) and `BodyControlSWC` (consumer via R-Port `R_DoorStatus`).
- **Traceability**: Citations pointing to Page 2 interface definition table.

### 3. Cross-Version Architectural Evolution
- **Question**: *"What changed between the available v1.0 and v2.0 information regarding the body control architecture?"*
- **Grounded Answer**: Accurately distinguishes changes between `v1.0` (baseline central locking) and `v2.0` (CAN FD migration, AUTOSAR Adaptive service-oriented interfaces, upgraded cryptographic boot authentication).
- **Traceability**: Citations referencing both `v1.0` and `v2.0` documents.

### 4. Negative Control: Insufficient Evidence Refusal
- **Question**: *"What is the exact ECU hardware part number?"*
- **Controlled Rejection**: *"Insufficient evidence in the selected HLD documents to answer this question."*
- **Traceability**: Zero hallucinations, 0.0 confidence score, and clear advisory notice explaining that hardware part numbers are not specified in the HLD evidence.

## Known Limitations

As documented in [docs/LIMITATIONS.md](file:///c:/Users/aasle/Downloads/autosar-hld-ai-assistant/docs/LIMITATIONS.md):
1. **Retrieval Confidence vs. Mathematical Certainty**: Confidence scores reflect retrieval similarity and chunk coverage, not formal mathematical certainty of the underlying model.
2. **Local Single-Node Vector Store**: ChromaDB runs as an embedded persistent client suitable for workstation and team deployments; multi-node distributed clustering is planned for enterprise scaling.
3. **Cross-Page Table Splitting**: Multi-page tables are indexed per physical page with page-specific headings.
4. **Multi-Version Ambiguity**: If querying across all documents without version tags, evidence from multiple revisions may be returned accompanied by an advisory limitations notice.
5. **OCR Latency**: Pages processed via the OCR fallback require additional image conversion time relative to direct digital vector extraction.

---

## Safety & Governance

- **Strict Grounding**: The LLM prompt prohibits extrapolation, external assumptions, or guessing.
- **Evidence Traceability**: Every engineering statement provides verified page numbers and section citations.
- **Controlled Refusals**: Incomplete or missing architectural details trigger explicit refusal rather than fabricated specs.
- **Human-in-the-Loop**: The assistant acts strictly as an advisory copilot; it does not approve software releases or alter source HLD documents.
